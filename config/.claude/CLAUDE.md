# Global Instructions

## Worktree

worktree を作成したら、そのプロジェクトの初期化手順（CLAUDE.md や README のセットアップ手順）を実行すること。依存インストールや設定ファイルの trust など、ルートリポジトリで済んでいるセットアップが worktree では未実施のため。

### wt コマンド

git worktree のライフサイクル管理は `wt` zsh 関数（`dotfiles/.zsh.d/wt.zsh`）で行う。ユーザーが worktree 作成・整理を希望した場合は以下を案内する：

| コマンド | 用途 |
|---|---|
| `wt new <branch>` | 既存ブランチ（local / origin）から worktree 作成 |
| `wt new pr <番号>` | PR の branch を fetch して worktree 作成 |
| `wt list` | worktree 一覧（PR ステータス付き） |
| `wt sweep` | merged / closed PR の worktree を一括削除（確認あり） |
| `wt rm <name>` | 個別削除 |
| `wt code` | VSCode の multi-root workspace を開く |

レイアウト規約：
- メインチェックアウトの sibling に `<repo>.worktrees/<name>/` を配置
- VSCode workspace ファイルは `<repo>.code-workspace`（sibling 配置）
- secret 等は `~/.config/wt/<repo>.symlinks` に列挙したファイルのみ symlink（コピーは行わない）

worktree を「気軽に作る・PR マージで sweep する」運用が前提なので、`git worktree add` を直接案内せず `wt new` を優先すること。

## コミットメッセージ

可能な限り日本語で書く。タイトル・本文ともに日本語を基本とし、技術用語（API 名、ファイル名、識別子）は英語のまま残してよい。これはどのプロジェクトでも共通。

**Conventional Commits 形式の prefix を付ける**: `type(scope): 要約`。type は `feat` / `fix` / `refactor` / `test` / `docs` / `chore` / `ci` など、その repo の慣習に合わせる。`(scope)` には変更対象を短く示す——対象の workspace（モノレポのパッケージ名等）や機能領域を入れる（例: `fix(ws):`、`feat(player):`、`refactor(auth):`）。

**簡潔に。何をしたか・なぜそうしたか・他に伝える必要があることだけを書く。** 以下は入れない：

- プロジェクトのフェーズ名や進捗ラベル（「Phase 2」「〜完了」等）。コミットは進捗管理ではない。
- 変更ファイルの逐一列挙。diff を見れば分かるので、本文は要点（何を・なぜ）に絞る。
- subject への冗長なスコープ前置き（長いプロジェクト名の繰り返し等。上記 `(scope)` は短く保つ）。

## PR の概要

**PR の文章もコミットメッセージも「後で読む人が分かる文」だけを書く（厳守）。** 今の自分・作業経緯・
ローカルの状態（未コミットだった／手元では〜等）など、読み手に無関係な事情は一切書かない。

次の構成で書く。簡潔に。

1. **冒頭**: 何の PR かを平文（1〜2文）で書く。見出しは付けない。
2. **## 背景**: なぜ出したかを箇条書き。
3. **## 実施内容**: 何をしたかを箇条書き。
4. それ以降: 検証内容など PR に必要な情報を軽く添える（任意で見出し）。

全体に長文化しない。冒頭の平文と「背景」には、ファイル名・クラス名・関数名等の詳細は書かない
（詳細は「実施内容」以降に）。これはどのプロジェクトでも共通。

## コードコメント

コードコメントは「**時系列や誰が読むかに関わらず、そのコードを読む人が必要とする・読んだ方がよい、コードからは読み取れない仕様や意図**」だけを書く。コードを読めば分かることや、コメントなしでも自明なことは書かない。

**今この瞬間の自分／レビュアー／会話相手にしか意味を持たないラベル・経緯は書かない。** 具体的には：

- 計画名・案名・フェーズ名・チケット番号等の進捗/会話ラベル（「案B」「§7」「Phase 2」「今回の変更」「core では」「恒久対応で」等）。
- 変更の経緯・before/after の説明（「〜していたが〜に変えた」「既存バグの解消」等）。差分は git が持つ。
- TODO に見せかけた自分用メモ（スコープの言い訳等）。本当に残すべき既知の制約なら、ラベルを外して「仕様上の制約」として書く。

書くべきは、コードから読み取れない**契約・単位・前提・不変条件・外部仕様の都合**（例：「引数は presentation time（絶対座標）」「この API は DVR 窓先頭からの相対秒を取る」「この値は更新の合間は外挿され鋸歯状に変動しうる」）。

### メソッド / API の doc

メソッドの doc は呼び出し側のための**契約**。ボディを読まずに使えるよう、**何をするか・呼ぶとどうなるか
（名前から読めない副作用含む）・いつ使うか（兄弟メソッドとの使い分け）・引数/戻り値の意味と単位・事前条件・
失敗時の挙動・落とし穴**のうち、該当するものだけ書く（全項目を機械的に埋めない）。

- **抽象度はそのメソッドに合わせる。** 包括メソッド（wrapper）の doc に、内部で扱う個別要素を列挙しない。
  例: 「現在ユーザを最新化する」メソッドの doc に token と plans を名指しで書くと、最新化対象が増減するたびに
  doc が腐るうえ、「呼び手は中身を気にせず最新化だけ知ればいい」という包括化の意図に反する。書くのは呼び手が
  知るべき抽象（何を保証するか・いつ呼ぶか・失敗時どうなるか）であって、実装の構成要素ではない。
- **特定の呼び出し元の事情を書かない。** doc はあらゆる呼び出し元に共通する契約。会話・口頭で出た「今この
  caller がこう使いたいから」は契約ではなくノイズで、呼び出しが変われば腐る。

## コードの空行・まとまり

コードには論理的な「まとまり」があり、**人はまとまり単位で読む**。空行はそのまとまりを区切る、意味のある構造要素として扱う。

- **空行を削りすぎない。** 関数内の論理ステップ（例：入力取得 → パース → 検証 → 本処理）の境目には空行を入れる。詰めて書くと読み手がまとまりを追えない。
- **構造体・クラスのフィールド定義も空行込みでレイアウトを検討する。** 関連するフィールドのグループを空行で分ける等。
- リファクタや整形で**機械的に空行を潰さない**。fmt が消さない空行は意図とみなす。

## ドキュメント（実装リポの docs/）

実装リポジトリの docs には**完成形（あるべき姿）を書く**。「Phase N で予定」「現状は〜」「実装中」等の
**途中経過・進捗・フェーズは書かない**。docs はその完成形に向かって実装するための仕様であって、進捗記録ではない。

途中経過・進捗管理はプロジェクト管理側（タスク管理リポの backlog / plan 等）の責務。実装リポの docs に混ぜない。

## ドキュメントの書き分け（決定 / 検討）

ドキュメントは「**決定内容（結論）**」なのか「**検討中・選定（複数候補から選ぶための、更新前提のもの）**」なのかを
意識して書き分ける。

- **決定内容のドキュメントには選定理由を基本的に入れない。** 採用した構成・仕様（結論）だけを書く。
  決定が後で更新されることはあっても、「なぜそれを選んだか」「比較した候補」は別ドキュメント
  （選定・検討用。例: `decisions.md`）に置く。
- 例外: そのドキュメント自体が「複数候補から選ぶためのもの」なら、比較・理由を含んでよい（それが目的だから）。

## コマンド実行ポリシー

### 大原則（allowlist の線引き）

- **取り返しのつかない操作は自動でやらない。必ず確認する。** rm・上書き削除、`--force`/`--force-with-lease`、
  `reset --hard`、push 済み履歴の書き換え、外向きのデプロイ等。これらは `permissions.allow` にも入れない。
  allowlist に載せてよいのは「可逆・ローカル・参照/追加系」だけ。
- **読める範囲（Read 権限）を広域グロブで自動許可しない。** `Read(//Users/<me>/**)` のようにホーム配下を
  丸ごと許可すると鍵・トークン（`~/.ssh`, `~/.aws`, `.mise.local.toml` 等）まで無確認で読めてしまう。
  アクセス可能範囲は `additionalDirectories` に**明示したものに限定**し、新しい範囲はユーザーに確認する。

settings.json の `permissions.allow` でも一部を allowlist 化しているが、運用方針として：

- **git**: push まで自動実行可。ただし他人の変更を上書きする操作（`--force` / `--force-with-lease`、共有ブランチへの `push --delete`、push 済みコミットを巻き戻す `reset --hard` など）は必ずユーザー確認を取る。
  - ブランチ切替は `git checkout` ではなく `git switch` を使う。理由：`git checkout` はブランチ切替とファイル復元（`checkout -- <file>` で uncommitted な変更を破棄）の両方を兼ねるため allowlist にしづらいが、`git switch` はブランチ切替専用で副作用がない（ファイル復元は `git restore` 側）。安全にブランチ切替できるので確認なしで実行できる。
- **gh**: 参照系（view / list / diff / checks / status / search / browse など）は自動実行可。変更系（pr create/merge/close/comment、issue create/comment、release create、repo create/delete など）は確認を取る。
- **その他のシェルコマンド**: 参照系（ls / find / grep / rg / ps / env / `--version` 系、書き込みを伴わない jq など）は自動実行可。ファイルやシステム状態を変更するコマンドはユーザー確認を取る。

### 確認プロンプトを避ける手段選択

同じ結果が得られるなら、確認プロンプトを出さずに済む安全な手段を優先する：

- ファイル閲覧は `cat` / `sed` / `awk` ではなく **Read ツール**（offset/limit で範囲指定可）
- ファイル検索は `find` を Bash で叩かず **Glob ツール**（`**/pattern` で表現できる範囲なら）
- 文字列検索は `grep` を Bash で叩かず **Grep ツール**
- パイプ・リダイレクト（`2>/dev/null`、`|`）を含むコマンドは shell metacharacter 判定で allowlist の prefix マッチ（`find:*` 等）が当たらず確認が走るので、専用ツールで代替できないか先に検討する
- `find` を Bash で叩くのは `-mtime` や複雑な `-not -path` の組み合わせなど、Glob で表現できない条件があるときだけ

## 作業開始前のブランチ確認

コード変更・コミット・push する前に、現在のブランチが安全に進められる状態か必ず確認する：

1. `git fetch` で remote の最新を取り込む
2. `git log --oneline @{u}..HEAD` / `HEAD..@{u}` でローカルと remote のずれを確認
3. `gh pr view <branch>` または `gh pr list --head <branch>` で PR の状態（open / merged / closed）を確認
4. **マージ済みブランチに追加コミットを乗せない**。PR が merged なら新しいブランチを最新 main から切る

特に「数日前のローカルブランチで作業継続」「PR レビュー対応の続き」など、コンテキストを切り替えた直後は要注意。ローカル視点だけで判断すると、マージ済みブランチに後付けコミットして混乱を招く（過去にやらかし済み）。

## 実装の進め方（TDD・少しずつ）

機能を実装するときは **TDD で小さく回す。一気に大きく作らない**（差分が大きいと本人が読めない）。

- サイクル: **小さくテストを書く → 落ちる(red)を確認 → 通すコードを書く → 通る(green) → 次へ**。これを繰り返す。
- 1 サイクル = 1 つの小さい振る舞い。複数の機能・レイヤを一度にまとめて実装しない。
- 本人が追えるよう、各サイクルで「何をテストし → どう落ち → 何を実装して通したか」を簡潔に見せながら進める。
- これは**コミット粒度とは別軸**。TDD サイクルごとに必ず 1 コミットする必要はない（コミットはトピック単位でまとめてよい）。
- 既存にテスト基盤が無い等で TDD が難しい場合は、その旨を先に伝えてから進め方を相談する。

## クラス・API 設計（場当たり的にシグネチャを生やさない）

メソッド・シグネチャ・フィールドを足す前に、**毎回**立ち止まって設計として検討する。目の前の要件を満たす
最短の追加を反射的に入れると、API が肥大化して使う側が混乱する（近視眼的な追加を繰り返さない）。都度、次を問う：

- **使う側が迷いなく使えるか**。呼び出し側の視点に立ち、自然な 1 つの呼び方へ導けているか。似て非なる
  メソッドが並んで「どれを使えばいいか」を迷わせていないか。
- **適度な隠蔽ができているか**。直接的で細かいメソッドを増やすほど使う側は混乱する。内部詳細は隠し、
  意図を表す少数の入口にまとめる。**新メソッドを足す前に、既存の抽象に乗せられないかを先に考える**。
- **ユーザーの意見を鵜呑みにしすぎていないか**。依頼どおりのシグネチャでも、設計として正しいかは自分で吟味する。
  筋が悪ければそのまま実装せず、理由を添えて代替を提案する（言われたから足す、をやらない）。
- **既存クラスの設計・意図を汲んでいるか**。そのクラスの責務・想定される使われ方を理解した上で変更し、
  既存の設計思想と整合させる。継ぎ接ぎでねじれた追加をしない。

実装前に都度かける観点。TDD で小さく回すときも、各サイクルの「通すコード」をこの観点で設計する。
迷ったら追加せず、設計の選択肢を提示して相談する。

## コード変更時の常時チェック観点

コードを変更したら、commit やレビュー依頼の前に以下を必ず確認する。どのプロジェクトでも共通：

1. **デグレ**: 既存のフローが壊れていないか。state の組み合わせや既存の caller を網羅的にチェック。
2. **プロパティリセットし忘れ**: 新規追加した state / field が destroy / stop / reset / 切替完了 等の節目で適切にクリアされるか。
3. **メモリリーク**: イベントリスナー、Promise、setTimeout、循環参照など、cleanup が必要なものが解放されるか。
4. **コメント不整合**: コード変更によって既存コメントの内容が古くなってないか。type 表記 (refactor/feat/fix) と実体が合ってるか。

普通の変更で見落としがちな観点。後で発覚すると修正コストが高い。レビュアーにも丁寧なコミットを提供できる。
